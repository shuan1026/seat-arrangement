# 決策紀錄

本專案的決策事項都記在這裡，包括待決議事項、已決議的決定與決策過程。其他文件需要提到某個決定時，引用這裡的條目編號，不要重複抄寫內容。

## 寫法

- 每個議題一個條目，編號依序為 D-001、D-002……，編號不重複使用。
- 新議題先放在「待決議」，寫上決議前先採用的做法。有了決定後，把條目移到「已決議」，補上決議內容與日期。
- 決議後來改變時，直接更新原條目，並在「過程」記下改了什麼、日期與原因，不要另開新條目。

條目格式：

```markdown
### D-001 議題名稱

- 狀態：待決議／已決議（YYYY-MM-DD）
- 背景：為什麼需要做這個決定
- 選項：考慮過的做法與各自的取捨
- 目前假設：決議前先採用的做法（待決議時填寫）
- 過程：討論經過，依日期記錄
- 決議：決定了什麼、由誰決定、為什麼
- 影響：需要同步修改的文件、原型頁面或程式
```

### D-001 正式版的資料持久化與技術選型

- 狀態：已決議（2026-11-10）
- 背景：需求要求資料存在資料庫，而且每一次編輯與拖移都要持久化；不需要登入與權限。目前只有 HTML 原型，資料存在開啟者的瀏覽器（`localStorage`），還沒有後端。
- 選項：
  - 部署平台：使用者指定公司的 aiborn 平台。平台的靜態網站沒有後端，無法安全地連資料庫，所以只能用動態網站（Docker 映像部署到 Cloud Run，平台提供 MySQL 8.4）。
  - Next.js 全端單一服務：頁面與 API 在同一個服務；使用者熟悉 Next.js；平台規格直接支援 Next.js standalone。
  - Next.js 前端 + 獨立後端（Express、FastAPI）：每個動態網站是一個服務，個人方案只有 1 個額度，拆開要佔兩個，還要處理跨網域與兩次部署。不採用。
  - API 用 Route Handlers 或 Server Actions：Route Handlers 有明確的 HTTP 契約與錯誤碼，方便做依序送出、可重試的儲存佇列，也方便整合測試；Server Actions 綁在頁面元件上，錯誤處理與重試要另外包裝。採 Route Handlers。
  - ORM 用 Prisma 或 Drizzle：平台規格預設用 Prisma 並在啟動前執行 `prisma migrate deploy`，採 Prisma。
  - 即時同步：需求已確認不做，不採用 WebSocket。
- 過程：
  - 2026-11-09 使用者提出需求時一併說明資料要存資料庫、每次操作都要持久化；先在原型以 Header 的儲存狀態呈現，技術做法留到需求確認後。
  - 2026-11-10 使用者指定部署到 aiborn 平台、說明熟悉 Next.js，請 Claude 選定技術方案。Claude 查 aiborn 原始碼與文件整理出平台限制（`docs/architecture.md` 第 2 節），選定下列方案；過程中發現網址公開的問題，另開 D-003。
- 決議：部署到 aiborn 動態網站；Next.js（App Router）全端單一服務，`output: "standalone"`，Node.js 24；API 用 Route Handlers + zod；MySQL 8.4 + Prisma；前端開頁一次載入全部資料，每個操作立即送出一個請求儲存；業務規則寫成前後端共用的純 TypeScript 模組。由使用者指定平台與框架方向、委由 Claude 選定細節。
- 影響：`docs/architecture.md` 全文；日後的 `docs/spec/`、`AGENTS.md` 的測試指令表（建立專案後補上）

### D-003 正式版網址的存取保護

- 狀態：已決議（2026-11-10）
- 背景：需求原本不需要登入。但 aiborn 動態網站的正式網址是公開的 Cloud Run 網址，任何拿到網址的人都能開啟；平台的成員名單只管靜態網站，不擋動態網站。正式版資料包含全公司員工的真實姓名、部門、分機與座位。D-002 只涵蓋原型。
- 選項：
  - 不加保護，只靠網址不外流：完全符合需求，但網址被轉傳或外流就看得到全部資料，任何人也都能修改或刪除。
  - 共用通行碼：第一次開啟時輸入一組通行碼（存在環境變數），之後用 cookie 記住；不做帳號，所有人權限仍相同。改動最小，但通行碼可能隨網址一起被轉傳。
  - Google 登入、只允許公司網域：平台可以申請 OAuth 用戶端；最安全，但改變「不需要登入」的需求，活動當天現場人員要先登入。
  - 只允許公司內網：平台的 Cloud Run 對外公開，無法限制來源 IP，不可行。
- 過程：
  - 2026-11-10 選定部署平台時，查 aiborn 原始碼發現動態網站一律是公開網址，列為待決議；Claude 建議共用通行碼。
  - 2026-11-10 使用者決定改採 Google 登入、只允許公司網域。
- 決議：使用者決定用公司 Google 帳號登入，只允許公司網域的帳號。登入只用來確認是公司同仁：登入後所有人權限相同，不分角色，不建帳號資料表。選擇最安全的做法，接受現場人員要先登入。
- 影響：`docs/architecture.md` 第 2、9、10、14、15、17、18 節；正式規格要把「不需要登入」改為登入，並加入登入頁、非公司帳號被拒與登出的畫面與文案；要告知承辦人；部署時要在平台申請 Google OAuth 用戶端。

### D-004 多人同時操作的衝突處理

- 狀態：已決議（2026-11-10）
- 背景：需求已確認不做即時同步，別人的改動重新整理後才看到。但兩人同時操作時，可能在別人已改過的資料上繼續操作，例如把人拖進一桌在自己畫面上還有空位、其實已被別人坐滿的桌。原本規格沒有這種情況的處理方式與文案。
- 選項：
  - 以操作為單位寫入，後端檢查規則：每個操作只送「這一步」，後端在交易內鎖桌次並檢查人數等規則；違反時拒絕，前端重新載入最新資料並提示。不違反規則的操作照樣成功，後送的覆蓋先送的。
  - 加版本號，任何衝突都拒絕：較嚴格，但輪流操作的情況下常被擋，體驗較差。
  - 整份資料存檔、最後存的覆蓋：實作最簡單，但會整份蓋掉別人的改動，不採用。
- 過程：2026-11-10 撰寫架構時提出，Claude 建議第一種；同日使用者同意照建議。
- 決議：使用者決定採第一種。後端在交易內鎖桌次並檢查規則，違反時拒絕；前端捨棄還沒送出的操作，重新載入最新資料並提示。違反桌次人數等規則時沿用既有文案（例如桌次已滿），其他情況顯示「資料已被其他人更新，已重新載入。」不違反規則的操作以後送的為準。
- 影響：`docs/architecture.md` 第 8.2、10.3、18 節；正式規格要補上這句文案。

### D-006 平行實作的方式

- 狀態：已決議（2026-11-10）
- 背景：實作計畫的階段 2 要四條功能線同時進行。專案不是 git repo，git 操作只由使用者做；專案規則要求每次改動都跑全部測試。
- 選項：
  - 同一個目錄、依檔案分工：不需要 git；但開發中一條線的測試會碰到別條線還沒完成的程式，只能先跑自己的測試，全部測試在階段結束時統一跑。
  - git worktree 隔離：每條線在自己的 worktree 隨時可以跑全部測試，最符合專案規則；要先 git init，由使用者 commit 基準版，各線完成後由使用者合併分支。
- 過程：2026-11-10 Claude 建議同一個目錄依檔案分工，使用者選擇 git worktree 隔離。
- 決議：使用者決定用 git worktree 隔離。階段 1 完成後使用者 git init 並 commit 基準版；每條線在自己的 worktree 與分支開發，用自己的測試資料庫與埠號，隨時跑全部測試；agent 不 commit，線完成後由使用者 commit 並合併回主分支。檔案歸屬規則照舊，用來減少合併衝突。
- 影響：`docs/plan/implementation-plan.md` 第 1、4、5、8 節；階段 1 的測試環境要能用環境變數指定測試資料庫名稱與埠號。

### D-007 正式版的真實名單用 seed 匯入

- 狀態：已決議（2026-11-10）
- 背景：架構原本規定程式與測試只用虛構資料，真實員工名單只透過正式環境畫面上的匯入功能進資料庫，不放進 repo 或映像。承辦人已提供公司通訊錄（員工名單）與 2026 年尾牙報名表（Google 表單匯出的 CSV，`docs/glossary/2026微程式感恩晚宴報名表.csv`），原型已改用 seed 直接載入這兩份資料。報名表的欄位和參與人員匯入的範本不同（Q7）。正式環境的資料庫只能從 Cloud Run 內部用私有網路連線，seed 只能在容器啟動時執行；Cloud Run 會冷啟動，seed 每次啟動都會跑。
- 選項：
  - 照原規則，上線後在畫面上匯入：不必特別處理，但報名表要先轉成參與人員匯入的範本格式。
  - seed 匯入，資料檔隨手動上傳的部署 ZIP 進映像：做法最簡單，不需要平台的其他功能；第一版映像會含真實姓名，資料留在平台內部。
  - seed 匯入，資料檔放在平台的磁碟區（雲端儲存掛載）：映像不含真實資料；但還要確認平台磁碟區怎麼放檔案，也要多一個掛載設定。
  - 在本機執行 seed 連正式資料庫：資料庫只開私有網路，不可行。
- 過程：2026-11-10 使用者提供報名表，要求員工名單與尾牙名單先用 seed 直接匯入。Claude 先套用在原型，並指出正式版和架構規則不同；同日使用者確認正式版也用 seed。具體做法由 Claude 選定為資料檔隨部署 ZIP。2026-11-10 寫 seed 測試時改了兩處：（1）鎖：原本用 MySQL `GET_LOCK`，但釋放鎖在交易 commit 之前，另一個執行個體可能在 commit 前拿到鎖、看到員工表還是空的而重複匯入，改為在交易內鎖住工作人員桌那一列（`SELECT … FOR UPDATE`），鎖到 commit 或 rollback 才放開；（2）Log：原本寫「對不到員工名單的人記在 Log」，和架構第 15.2 節與 Log 規範「不記姓名」矛盾，使用者決定 Log 只記筆數，部署前由 Claude 在本機用真實資料試跑 seed，把對不到與會被略過的人名列在對話中給使用者。
- 決議：
  - 使用者決定正式版也用 seed 匯入員工名單與尾牙報名表。
  - 資料檔放在 `prisma/seed-data/`，加入 `.gitignore`，不進 repo。檔案是 `roster.csv` 與 `registrations.csv`。`roster.csv` 是通訊錄匯出檔，最後加一欄「組別」，格式同員工名單匯入範本。`registrations.csv` 是 Google 表單匯出的報名表原檔。
  - 只有手動上傳的部署 ZIP 會帶這兩個檔。GitLab CI 用 `git archive` 打包，不會帶。
  - seed 只在員工表是空的、而且兩個檔都存在時才匯入。匯入在同一個交易內完成，交易一開始鎖住工作人員桌那一列（`SELECT … FOR UPDATE`，鎖到 commit 才放開），避免多個執行個體同時匯入。員工表已有資料時跳過並記 Log，不會蓋掉上線後的修改。
  - 員工名單沿用 `roster-import.ts` 的規則。報名表用新的 `registration-import.ts`：只收會參加的人；同一人填好幾次時以最後一次為準；以姓名對應員工名單，同名再用部門判斷；眷屬、兒童椅、素食與備註照表單。對不到員工名單的人不匯入；Log 只記筆數，不記姓名，人名由部署前的本機試跑確認。電子郵件與填寫時間不存。
  - 匯入成功後，之後部署的 ZIP 不再帶資料檔，只有第一版映像含真實名單。上線後的異動用畫面上的功能處理。
  - 開發與測試仍只用虛構資料；`registration-import.ts` 的測試用虛構的表單 CSV。
- 影響：`docs/architecture.md` 第 6、7.3、11.2、14.1、14.3、19 節；`docs/plan/implementation-plan.md` 階段 1 的資料與階段 4；`.gitignore`；`docs/spec/` 的參與人員規格要寫出報名表的格式（與 Q7 一起確認畫面上的匯入是否也接受這個格式）。

### D-014 員工名單新增「不參加」報名狀態

- 狀態：已決議（2026-11-10）

  - 改權限：檢視者升為編輯者直接儲存；編輯者降為檢視者會失去編輯權限，和移除一樣先確認；改自己另外提醒；最後一位編輯者不能移除，也不能降為檢視者。
  - 移除：檢視者與編輯者都要確認；移除後只能看發布頁。
  - 生效時間沿用 D-021「從下一次開啟頁面或操作起」：被移除的檢視者下一次開啟、重新整理或匯出時看到「沒有權限」頁；被移除的編輯者下一次修改不儲存，接著顯示「沒有權限」頁；被降為檢視者的編輯者照 AUTH-R13；被加入的人重新整理就看得到。
  - 名稱：規格裡指「不在名單上的人」的「只能檢視」改稱「檢視者」；Header 的徽章仍寫「只能檢視」，說明的是能做什麼。
  - Claude 補充、使用者在確認摘要時同意的細節：「沒有權限」頁顯示在原本開的網址，不另外跳轉，加入後重新整理同一頁就看得到；伺服器也檢查最後一位編輯者，同時降級或移除時不儲存並重新載入；沒有權限的人開 `/permissions` 也是「沒有權限」頁，檢視者開 `/permissions` 照舊導向座位安排。
- 決議：
  - 身分分三種：編輯者（全部功能）、檢視者（D-021 的只能檢視：三頁內容相同、可以匯出、編輯入口隱藏、Header 顯示「只能檢視」）、沒有權限（其他公司帳號，只能看發布頁 `/seats`；三頁、讀取資料的 API 與匯出都被拒絕）。
  - 權限頁是一份名單：新增時輸入 email、選權限（預設檢視者），只接受公司網域，一次一個；每列有權限選單與「移除」，依加入的先後排列。區塊標題「新增帳號」、清單標題「帳號」。
  - 改權限、移除、最後一位編輯者、改自己與移除自己的規則與文案見 `docs/spec/permissions.md` 第 3.2、4.1 節。
  - 新增「沒有權限」頁：置中卡片、不套 App Shell，標題「你沒有檢視權限」、說明、目前登入的 email、「查看座位表」與「登出」。
  - 檢視者不另設環境變數；`INITIAL_EDITOR_EMAILS` 與發布頁、發布對話框都不變。
  - 不寫進 `docs/product-spec.md`；權限頁與「沒有權限」頁沒有原型，不用同步。
- 影響：`docs/spec/README.md`（第 2、4、8.3 節、COM-R19、共用文案、驗收條件）、`docs/spec/permissions.md`（第 1、2.1、3.1、3.2、4.1、5.1、5.2 節）、`docs/spec/{seating,participants,employees}.md`（只能檢視的人改稱檢視者）、`docs/architecture.md`（名單資料表加權限欄位、讀取 API 的權限檢查、權限頁 API）、`docs/plan/implementation-plan.md`。部署這一版後，名單上只有原本的編輯者，其他同仁會立刻看不到三頁，要由編輯者在權限頁加成檢視者；部署前先準備好要加的檢視者名單。

### D-027 桌子可以新增、刪除、搬動，場地旁加暫存區

- 狀態：已決議（2026-11-11）
- 背景：原本座位圖固定 30 桌，使用者不能新增、刪除或搬動桌次（SEAT-R01），整桌換位置只能拖把手兩兩對調，或用「調換桌次…」。實際排座時常要一次調整好幾桌的位置，兩兩對調很難用；每年需要的桌數也不一定剛好 30 桌。使用者要讓桌子可以編輯、新增、刪除、調整數量，30 個位置仍然固定，並可以把桌子從場地拉到旁邊的暫存區，原位置顯示沒有放桌。
- 選項與過程：2026-11-11 以 `/grill-me` 討論三輪，Claude 每題提出建議，使用者除了一題外全部採用：
  - 桌號跟著什麼：桌號跟著位置（A1～A15、B1～B15），名單與備註名稱跟著桌子；桌子搬到哪個位置就是那個位置的桌號，暫存區的桌子沒有桌號。和原本對調時「桌號與位置不變」一致。
  - 沒有桌子的位置：和「空桌」（有擺桌、沒有人）分開，叫「未放桌」；不算空位與已滿，匯出時空白，自動排座跳過，發布頁不顯示。Claude 原本建議「未放桌」不加外框，使用者要求在座位圖上用虛線框出範圍；空桌原本就是虛線邊框，所以「未放桌」改成只有虛線外框、沒有底色與陰影，空桌維持卡片底色加虛線，用有沒有底色與文字區分。也考慮過把空桌改回實線，但空桌的虛線在座位安排頁與發布頁都已在用（D-025），沒有採用。
  - 暫存區的人算不算入座：算未入座（統計、匯出的未入座區塊、發布頁搜不到），徽章顯示「暫存」；另一個選項是算入座，但他們沒有桌號，匯出、發布頁與所有顯示桌號的地方都要另外處理，沒有採用。
  - 新增桌：在「未放桌」的位置新增，一步完成也看得到位置；另一個選項是在暫存區新增再拖到位置，多一步，沒有採用。
  - 刪除桌：有人的桌也可以刪，先確認，人回到未入座，備註名稱一併刪除，可以復原；另一個選項是只能刪空桌，要先清空，沒有採用。
  - 暫存區的位置：畫在場地圖上 B 區右側，跟著縮放與平移；另一個選項是座位圖區上方一條不縮放的橫向區塊，拖桌子要跨區域，沒有採用。左側有人員面板、右側會浮出桌次詳情，所以不做固定在旁邊的一欄。
  - 暫存的桌子怎麼稱呼：沒有桌號，座位圖上放桌號的位置寫「暫存」，詳情標題「暫存區的桌」，有備註名稱時加上備註名稱；不另外編號。
  - 拖桌子的規則：場上的桌拖到有桌子的位置是對調（同原本）、拖到「未放桌」是搬過去、拖到暫存區是移出；暫存的桌拖到「未放桌」是放上去、拖到有桌子的位置是交換（原本那桌改到暫存區）。「調換桌次…」保留，暫存的桌另有「放到…」。
  - 暫存的桌子能做什麼：只能整桌操作（放回、刪除、看名單、改備註名稱），人不能放進去，可以把人拖出來或移出；另一個選項是和場上的桌一樣可以加人、調整順序，沒有採用。
  - 手機：桌次詳情的按鈕取代拖移（「調換桌次…」「移到暫存區」「刪除桌」「放到…」，「未放桌」的面板有「新增桌」）。
  - 自動排座：「未放桌」跳過；暫存區的桌與上面的人都不動，「只排未入座」不把他們拆開排進場上，「清空後重排」也不清空暫存區。另一個選項是把暫存區的人當未入座排進場上，會拆散整組，沒有採用。
  - 新增與刪除的畫面、文案、復原範圍、多人衝突沿用現有提示、參與人員頁的「暫存」徽章與桌次選項，都照 Claude 的建議。
  - Claude 補充、使用者在確認摘要時同意的細節：工作人員桌不受影響；現有 30 桌都留在原位置；「調換桌次…」列出其他 29 個位置，「未放桌」寫成「{代碼}（未放桌）」；「全部展開」時暫存的桌一起展開；檢視者看得到暫存區與「未放桌」，但沒有把手、「新增桌」「刪除桌」，點「未放桌」沒有反應；發布頁不畫暫存區。
- 決議：
  - 場地有 30 個固定位置 A1～A15、B1～B15，位置的數量與排列不變；每個位置可以放一張桌子或「未放桌」。桌子（名單、順序、備註名稱）可以新增、刪除、在位置之間搬動或移到暫存區。桌號是桌子所在位置的代碼，暫存的桌沒有桌號。
  - 「未放桌」：座位圖上是虛線外框、沒有底色與陰影，中間是變淡的位置代碼與「未放桌」；不算空位與已滿，匯出時空白，自動排座跳過，發布頁不顯示，人不能放進去。點它開啟面板，可以「新增桌」。
  - 暫存區：場地圖上 B 區右側的一欄，跟著縮放與平移；暫存的桌依移入的先後由上往下排。暫存的桌上的人算未入座，徽章「暫存」；人不能放進暫存的桌；暫存的桌可以放回、刪除、看名單、改備註名稱。自動排座不動暫存區。
  - 拖桌子的把手：場上的桌 → 有桌子的位置對調、→「未放桌」搬過去、→ 暫存區移出；暫存的桌 →「未放桌」放上去、→ 有桌子的位置交換。手機用桌次詳情的按鈕。
  - 刪除桌：有人也可以刪，Alert Dialog 確認，人回到未入座、備註名稱刪除。搬動、移到暫存區、放回、新增、刪除都可以復原；多人衝突沿用「資料已被其他人更新，已重新載入。」。
  - 工作人員桌不變。不寫進 `docs/product-spec.md`；座位安排頁的原型還沒改，需要時用 `/sync-prototype` 同步。
- 影響：`docs/spec/seating.md`（範圍、座位圖、桌次樣子、桌次詳情、新增與刪除、拖桌子規則、統計列、復原、手機、檢視者、文案、驗收條件）、`docs/spec/auto-arrange.md`、`docs/spec/export.md`、`docs/spec/participants.md`、`docs/spec/permissions.md`、`docs/spec/README.md`、`docs/architecture.md`（桌子與位置分開的資料、桌子的指令、migration）、`docs/plan/implementation-plan.md`。部署後現有 30 桌都在原位置，畫面和部署前相同。

### D-028 座位操作可以復原與重做最近 20 步，工具列加「復原」「重做」

- 狀態：已決議（2026-11-11）
- 背景：原本座位的操作完成時以 Sonner 帶「復原」，只能復原最近一次（SEAT-R77），Sonner 約 6 秒後消失就不能復原。使用者要有「最近步驟的前進、後退」按鈕。
- 選項與過程：2026-11-11 以 `/grill-me` 討論一輪，Claude 每題提出建議，使用者全部採用：
  - 按鈕位置：座位安排頁座位圖工具列的最左邊（「縮小」前面）；另一個選項是放在 Header 每一頁都有，但員工名單頁沒有可以復原的操作，按鈕會一直停用，沒有採用。Tooltip 寫出那一步的提示，步驟多時才知道在復原哪一步；檢視者不顯示。
  - 步數與清掉的時機：最多 20 步；重新整理、別人改過資料而重新載入、被移除編輯權限時清掉；可以記的操作和原本可以復原的相同，不能復原的操作（備註名稱、人員的新增編輯刪除）不會清掉紀錄。
  - 重做：復原後可以一步一步重做；做了新的可以復原的操作就不能再重做；復原後 Sonner「已復原。」、重做後「已重做。」，都不帶按鈕；中間別人改過相關資料時不儲存、重新載入並清掉紀錄。
  - Sonner 的「復原」：保留，等於復原最近一步；另一個選項是拿掉，但參與人員頁沒有工具列，在那裡做的操作就沒有地方復原，沒有採用。
  - 鍵盤快捷鍵（Ctrl+Z、Ctrl+Shift+Z）：不加，是沒有提到的額外功能，之後需要再加。
  - Claude 補充、使用者在確認摘要時同意的細節：「重做」的 Tooltip 是「重做：{那一步的提示}」；用工具列復原時那一步的 Sonner 一起關掉；一步要等儲存完成才記進紀錄；兩個按鈕的無障礙名稱是「復原」「重做」，步驟內容寫在 Tooltip。
- 決議：
  - 座位安排頁座位圖工具列最左邊加 Icon Button「復原」（`undo-2`）與「重做」（`redo-2`），沒有可以復原或重做的步驟時停用；Tooltip「復原：{提示}」「重做：{提示}」；手機也有；檢視者沒有。
  - 最多記最近 20 步可以復原的操作（含參與人員頁做的座位操作），超過時拿掉最舊的；重新整理、重新載入、被移除編輯權限時清掉。
  - 可以連續復原、再一步一步重做；做了新的可以復原的操作就不能再重做。Sonner「已復原。」「已重做。」。
  - Sonner 的「復原」保留，等於復原最近一步。不加快捷鍵。
  - 不寫進 `docs/product-spec.md`；座位安排頁的原型還沒改，需要時用 `/sync-prototype` 同步。
