# Sync Prototype

把規格的改動同步到 HTML 原型。方向只有一個：規格 → 原型。

- **依據：** `docs/product-spec.md`。
- **可以改：** `ui-design-system/source-reference/html/` 底下的頁面與 `prototype/`。
- **只讀：** `docs/product-spec.md`、產品資料，以及設計系統的 `SKILL.md` 與 references，都不要改。`token-gallery/` 也不要改。
- **其他文件：** 先忽略，不讀也不改。

規格是依據，所以兩邊不一致時只改原型。覺得規格有問題就告訴使用者，不要改規格，也不要照自己的判斷做。

這個 skill 要跑得快：先用腳本比對，不要整份讀規格或頁面檔；同時需要的查詢放在同一輪發出。

## 1. 確定範圍

依序判斷：

1. 使用者指定了 Q 編號、章節或頁面：同步這些。
2. 同一個對話剛跑完 `/grill-me` 或 `/to-questionnaire`：用它列出的改動。
3. 使用者要全站掃描：範圍是 `all`。
4. 都沒有：問使用者要同步什麼，不要自己掃全站。

完成條件：能寫出這次的範圍。

## 2. 找出落差

先跑比對腳本，範圍用空白隔開。也可以傳功能區（`7.2`）或全站（`all`）：

```bash
node .agents/skills/sync-prototype/scripts/compare.js Q8 Q31 7.2.1 leads.html
```

腳本只印有問題的地方：

- **確認事項：** 題目或目前假設不同、原型沒有這題、畫面上沒有確認點。
- **文案在原型找不到：** 可能真的缺，也可能只是描述不是實際文案，或沒有畫面（例如 Email）。腳本會一併印出規格第 3.5 節，那裡列為原型不呈現的不用補，也不用列。
- **規則與描述：** 範圍內腳本比不了的規格內容。這就是規格原文，不用再讀規格。
- **頁面上寫死的數字：** 逐筆和示範資料核對，數字對不上就算要改，不要因為項目多而省略。
- **頁面上有、規格找不到的文字：** 用來找原型有、規格沒有的內容。

腳本沒印出來的文案和確認事項視為一致，不用再查。印出來的項目和「規則與描述」才要看原型：用 grep 找到相關程式，只讀前後幾行，頁面檔和 `prototype/` 的共用檔都不要整份讀。「規則與描述」要逐條判斷，一致的不用寫出來，但不能因此少比。

全站掃描時腳本不印規則，只比文案與確認事項，不要自己逐頁比對。一次回報全部，最後說明規則和版面沒比，使用者可以指定功能區（例如 `/sync-prototype 7.2`）再比。

同一項改動可能分散在好幾處，以下路徑都在 `ui-design-system/source-reference/html/`：

| 規格內容 | 原型位置 |
|---|---|
| 第 7 節的頁面、欄位、文案與規則 | 對應的 `<頁面>.html`；共用元件與對話框在 `prototype/ui.js`，App Shell 在 `prototype/shell.js` |
| 第 8 節業務規則 | `prototype/core.js` |
| 第 9 節的題目與目前假設 | `prototype/data.js` 的 `Q`；畫面上的確認點是 `UI.pin('Qn')` 或 `data-q="Qn"` |
| 第 1.2 節情境、第 4.4 節示範資料 | `prototype/data.js` |
| 第 4.3 節示範工具列 | `prototype/shell.js` |
| 第 6 節的通用規則，例如資料表格要有分頁 | 範圍內的每個頁面 |

確認事項的題目文字要和規格一致。規格的「目前假設」引用章節時（例如「第 8.1 節」），原型要寫出內容，因為客戶看不到規格；內容對得上就不用列。第 9 節新增的題目，在「影響畫面」中最主要的頁面加一個確認點。既有題目已經有確認點時不要再加，確認點不需要出現在每個受影響的畫面。

原型才有的內容，先問：做成正式產品後，它還會在嗎？

- **不會，只為了示範：** 不用理會，不列也不刪。例如模擬事件、主頁切換錯誤訊息的示範控制項、「原型不會產生實際檔案」這類提示，以及只有靠示範工具才看得到的狀態。
- **會，只是規格沒寫：** 列在「原型有、規格沒有」，不要刪。例如通知、列操作、狀態值，這些使用者可能會寫回規格。

這次規格改動明確拿掉的內容，原型還留著就算要改。規格沒寫清楚、自相矛盾，或需要新的 token、元件、版型時，列在「要你決定」，不要自己決定或發明。

### 回報落差

範圍內都一致，也沒有其他要列的內容時，只回一句「<範圍>：都一致，不用改。」，不用說明比對過程，也不用開伺服器。

有項目要列時，先用第 4 步的方式開好本機伺服器，不用另外測試，清單裡的連結才點得開。然後照下面的格式回報，等使用者確認後才改：

```markdown
第 7.2.8 節、Q5：要改 1 項，要你決定 1 項，檔案都還沒動。

## 要改

### 1. 客戶線索：未分派的卡片少了指派按鈕

- **怎麼看：** 切到業務主管 → 開[客戶線索](http://localhost:4173/source-reference/html/leads.html) → 點「未分派」→ 看第一張卡片
- **現在：** 只有「查看」
- **要改成：** 加上「指派」（第 7.2.8 節）

## 要你決定

### 2. 客戶詳情：匯出的欄位規格前後不一致

- **怎麼看：** 開[客戶詳情](http://localhost:4173/source-reference/html/customer-detail.html) → 按「匯出」
- **問題：** 第 7.4.2 節寫 8 欄，第 8.1 節寫 10 欄
- **建議：** 以第 7.4.2 節為準

## 原型有、規格沒有

- **主管的待分派通知：** 切到業務主管 → 按右上角通知 → 有「有 3 條新線索等待分派。」，第 7.1.2 節沒有這種通知。
```

- **只列要處理的：** 一致的項目不要列，也不要寫「其他都一致」的摘要。腳本印出來、判斷後不用處理的項目也不要提，不用解釋為什麼排除。使用者要知道的是該看哪裡、該決定什麼。
- **直接開始：** 第一句就寫範圍和數量，不要交代比對過程或伺服器狀態。
- **省略空區塊：** 沒有內容的區塊整段不寫。這一步還沒改檔案，也不用回報驗證。
- **編號連續：** 編號跨區塊連續，使用者才能直接回「1 改，2 照建議」。
- **內容要短：** 「現在」和「要改成」只寫不一致的那一句，不要貼整段規格，也不用寫程式位置。
- **項目多時：** 同一頁的零星文字併成一項；「原型有、規格沒有」只列會影響操作或判斷的內容。

「怎麼看」要讓使用者照著按就看到問題，不用讀程式：

- 用畫面上的名稱，寫清楚視角、入口、要點什麼和看哪裡。連結用伺服器指令印出的網址。
- 畫面會隨條件改變時，把條件寫進步驟。例如業務視角打不開成員頁，要先用示範工具列切到系統管理員。
- 每一步都對照頁面程式，確認真的點得到。不確定就用瀏覽器走一次。
- 畫面上看不到的內容（例如只存在程式裡的判斷），直接寫「畫面上看不到」和檔案位置，不要編步驟。

完成條件：要列出的項目都有「怎麼看」，其餘都判定為一致。

## 3. 修改

只改文案、確認點或示範資料時，不用讀設計系統，直接改。

動到元件或版面時，先讀 `ui-design-system/.cursor/skills/ui-design-system/SKILL.md`，依 Progressive Loading 只載入用到的章節，並照 Spec Execution Protocol 做。這裡要改的就是專案 HTML，所以內容、文案與規則以規格第 7 節為準；元件形狀與狀態以 `03-components.md` 為準；顏色、字級與間距用語意 token。

只改確認過的項目，不要順手重構或調整其他版面。修改時發現還要改別的地方，先問使用者，不要改完才告知。

完成條件：確認過的每一項都已改好。

## 4. 驗證

用本機伺服器開啟原型，有些瀏覽器工具無法檢查直接開啟的檔案。在專案根目錄執行 `node .agents/skills/sync-prototype/scripts/serve.js ui-design-system 4173`，再開 `http://localhost:<port>/source-reference/html/<頁面>.html`。指令會沿用同一個目錄已開的伺服器；port 被其他目錄占用時會自動換一個，所以 port 以指令印出的為準，不要自己判斷現有的伺服器能不能用。Claude 桌面版可以直接用 `.claude/launch.json` 的 `prototype`。

示範資料存在瀏覽器（`localStorage 的 `seat-arrangement-prototype-v1`）。改了示範資料時，先按示範工具列的「重設資料」，否則看到的還是舊資料。

每個改到的頁面至少截 320 px 和桌面兩種寬度，工具能批次操作時一次做完，並檢查：

- 改到的內容和規格一致
- 改到確認點時，按示範工具列的「顯示確認點」，點開後題目和目前假設都正確
- 整頁沒有水平捲動，元件沒有被裁切
- Console 沒有錯誤
- 內容會隨視角或資料狀態改變時，用示範工具列切換後也看過
- 改到 `prototype/` 的共用程式或樣式時，其他用到這段的頁面也看過（`data.js` 的確認事項文字不算）

發現問題就修，再驗證一次。工具沒有現成的瀏覽器或截圖功能時，不要為此下載或安裝工具；照實說沒有驗證，列出待人工檢查的頁面，不要回報完成。

完成條件：每個改到的頁面都有兩種寬度的結果，或已說明沒有驗證。

## 5. 回報

- **改了什麼：** 每個頁面或檔案一句話
- **驗證：** 一句話寫截了哪些頁面和寬度，只細寫發現的問題
- **還沒處理：** 等使用者決定的項目，用編號帶過。沒有就省略

不要重列第 2 步的內容或已一致的地方。改了示範資料時，提醒使用者要按「重設資料」才看得到。

也提醒使用者線上原型還沒更新，可以用 `/publish-prototype` 更新。這個 skill 不負責發佈。
